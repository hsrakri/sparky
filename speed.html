what actually moved the needle

Four moves. Both models win.

The orchestrator fronts the conversation; the coder does the heavy lifting. Each got a targeted speedup, then we changed how they work together.

MOVE 01 · CODER

MTP was hiding in the checkpoint

The NVFP4 weights ship a trained multi-token-prediction head. Turning it on — method:mtp, n=3 — nearly tripled decode. Unlike n-gram, tool-calls stay clean. No new image needed.

11.6→30.4 tok/s2.6×
MOVE 02 · ORCHESTRATOR

Swap the harness to a fast MoE

Replaced a 30B reasoning model (forced-eager, ~50 tok/s) with Qwen3.6-35B-A3B — a 3B-active MoE that runs CUDA graphs + MTP. Same clean tool-calls, half the latency per turn.

51.7→105.6 tok/s2.0×
MOVE 03 · WORKFLOW

Put the thinking where it's cheap

Reasoning is cheap on the 105 tok/s orchestrator and expensive on the 30 tok/s coder. So the orchestrator thinks hard; the coder thinks medium and executes. Delegation turn dropped from 6.85s to 2.72s.

6.85s→2.72s / turn2.5×
MOVE 04 · QUALITY

Fast hands, sharp eyes

The fast MoE drafts; the stronger 27B critiques & improves — only for complex code. In one test it caught 3 real bugs the draft missed (an unlocked __repr__ race, a bool-is-int validation gap, a liveness-only test).

        "num_speculative_tokens":3}' \
  --attention-backend flashinfer \
  --enable-prefix-caching \
  --tool-call-parser qwen3_coder \
  --enable-thinking # medium, it critiques \
  --gpu-memory-utilization 0.45
⚠ Co-location rules (learned the hard way)
  • Utils are per-process shares of the whole pool — they must fit free memory and sum ≲ 0.88 (0.42 + 0.45 here). Not a device-wide ceiling.
  • Start sequentially, coder first — starting both at once races; the second dies with "no available memory for the cache blocks."
  • MTP head loads from the checkpoint — no draft model, no third-party build; the stock v0.26 aarch64 image already registers the arch.
  • --restart no + one ordered boot script — Docker auto-restart re-introduces the race on reboot.
