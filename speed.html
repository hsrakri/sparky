Two experiments: one flat, one big

Not every knob pays off — and the ones that do aren't always the ones you'd expect. Both measured on the box, temperature 0.

EXPERIMENT · CODER · ✗ no gain

Bigger batch budget didn't move decode

vLLM warned the MTP scheduler caps max_num_scheduled_tokens at 2048. So we raised --max-num-batched-tokens to 8192 and re-measured single-stream code decode. Result: statistical noise — and it ate memory headroom, so we reverted it.

27.0→27.7 tok/sflat · reverted

Lesson: single-stream MTP decode is already at the memory-bandwidth ceiling. The batch budget only helps prefill and concurrency, not one-request tok/s.

EXPERIMENT · ORCHESTRATOR · ✓ shipped

Turning the router's brain down made it better

The literature calls it the "reasoning trap": a verbose chain-of-thought steals the attention an orchestrator needs to read requests and route. We A/B'd our orchestrator's thinking on vs off across 3 plan-and-delegate tasks.

580 tok · 5.4s→299 tok · 2.9s2× faster

Lesson: ~half the tokens, ~46% lower latency, and delegation quality held at 3/3 clean. Light, decisive routing beats heavy deliberation — we shipped thinking-off for the orchestrator, kept the coder at medium (it's the one that hallucinates).

what moved the needle

Four moves. Both models win.

MOVE 01 · CODER

MTP was hiding in the checkpoint

The NVFP4 weights ship a trained multi-token-prediction head. Enabling it — method:mtp, n=3 — nearly tripled code decode, with tool-calls intact. No new image needed.

11.6→30.4 tok/s2.6×
MOVE 02 · ORCHESTRATOR

Swap the harness to a fast MoE

Replaced a 30B reasoning model (forced-eager, ~50 tok/s) with a 3B-active MoE running CUDA graphs + MTP. Same clean tool-calls, half the latency per turn.

51.7→105.6 tok/s2.0×
MOVE 03 · WORKFLOW

Think where it's cheap

Reasoning lives on the 105 tok/s orchestrator (thinking: high); the 30 tok/s coder thinks medium and executes. The delegation turn collapsed.

6.85s→2.72s / turn2.5×
MOVE 04 · QUALITY

Fast hands, sharp eyes

The MoE drafts; the stronger 27B critiques & improves — complex code only. First trial: it caught 3 real bugs the draft missed (an unlocked __repr__ race, a bool-is-int gap, a liveness-only test).

  --speculative-config '{"method":"mtp",
        "num_speculative_tokens":3}' \
  --attention-backend flashinfer \
  --enable-prefix-caching \
  --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  # enable_thinking: true — it critiques
  --gpu-memory-utilization 0.45 \
  --max-model-len 131072 --max-num-seqs 32
⚠ Co-location rules (learned the hard way)
  • Utils are per-process shares of the whole pool — must fit free memory and sum ≲ 0.88 (0.42 + 0.45 here). Not a device-wide ceiling.
  • Start sequentially, coder first — simultaneous starts race; the loser dies with "no available memory for the cache blocks."
  • MTP loads from the checkpoint — no draft model, no third-party build; stock v0.26 aarch64 registers the arch.
  • --restart no + one ordered boot script — Docker auto-restart re-introduces the race on reboot.
  • A third model doesn't fit — a 35B MoE + MTP fails engine-init below ~0.30 util. Two residents is the sweet spot.

At 105 tok/s, reasoning is nearly free. It plans, decomposes, writes the first draft, and hands the coder a precise spec — signatures, file paths, test expectations.

At 30 tok/s, tokens are precious. Medium thinking is the sweet spot for its critic role — deep enough to spot an unlocked __repr__, cheap enough to stay responsive.
