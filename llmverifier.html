Self-Verification on a Dual DGX Spark Cluster

Running llm-as-a-verifier best-of-N selection with DeepSeek-V4-Flash as both generator and verifier, on self-hosted vLLM — including the reasoning-parser bug that silently flattens every score to 0.5, its root cause, the fix submitted upstream, and measured selection results.

With thanks to the llm-as-a-verifier authors for the framework, the prefill-scoring method, and the published Terminal-Bench self-verification results that motivated this work.
By the Sparky Desk · Filed from the rack
Summary
  • ①Goal: reproduce self-verification (same model generates N candidates and ranks them) on a self-hosted 2× DGX Spark vLLM cluster serving DeepSeek-V4-Flash-0731. Published gains: 79.4% → 86.5% (best-of-3), 88.0% (best-of-5) on Terminal-Bench 2.1.
  • ②Defect found: on any OpenAI-compatible server running a reasoning parser, every score collapses to the library's 0.5 fallback and selection is arbitrary. No error is raised.
  • ③Root cause: the prefilled score token is returned in message.reasoning, not message.content; the resulting empty token re-matches the score tag and the closing-tag placeholder overwrites the captured logprob distribution.
  • ④Fix: read the letter from the reasoning field; forbid empty-token tag re-matches. Submitted as PR #7 (issue #5). Verified: 0.91 vs 0.73 pairwise; best-of-3 selects correctly at 4 evaluation passes.
  • ⑤Deployment: ~26 min per reliable selection at cluster throughput → deployed as an unattended batch tool (N candidates at spread temperatures, self-verified selection, full run log), not an interactive one.
1 · Method Under Test

llm-as-a-verifier (MIT, arXiv 2607.05391) implements best-of-N selection: N candidate solutions are compared pairwise by a verifier LLM against named criteria, with a pivot tournament reducing the comparison count from O(N²) to O(Nk). Scores are not parsed from free text. The library appends a <score_X> tag to the verifier's analysis, requests exactly one further token constrained to a 20-letter scale (vLLM continue_final_message + structured outputs), and reads the full top-logprob distribution at that position — an expectation over the scale rather than a single sampled grade.

The relevant published result: with deepseek-v4-flash as both generator and verifier, Terminal-Bench 2.1 pass rates rise from 79.4% (pass@1) to 86.5% with best-of-3 and 88.0% with best-of-5. The test platform here serves the same checkpoint (DeepSeek-V4-Flash-0731, NVFP4, TP=2 across two GB10 nodes over 200 Gb RoCE, DSpark MTP-5, --reasoning-parser deepseek_v4), so the configuration matches the paper's headline case, self-hosted.

2 · Observed Defect

Pointing the library at the cluster's OpenAI-compatible endpoint produced uniform scores of exactly 0.5 for every candidate on every criterion — the library's documented fallback when no score can be read — making the returned winner an artifact of list order. Thirty calls completed without a single raised error. Server logs confirmed the requests executed and generated normally: the verifier was producing verdicts; the client was discarding them.

Replaying the library's prefill request manually against the endpoint isolated the discrepancy. The server returns a correct, grammar-constrained letter distribution in logprobs — but the sampled token itself arrives in message.reasoning with message.content = null, because the reasoning parser classifies a continuation without a closed think-block as reasoning content. This is standard behavior for any self-hosted DeepSeek deployment, including every DSpark-recipe server.

3 · Root Cause

The failure requires two interacting details. First, _score_tags_by_prefill reads the score letter from message.content; with the parser active this is empty, so the token recorded at the score position is the empty string. Second, _find_tag_logprobs selects the last position at which the accumulated text ends with the score tag — a deliberate rule, meant to skip mid-analysis mentions of the tag. Appending an empty token leaves the accumulated text unchanged, so it still ends with the tag; the rule re-matches one position late and returns the placeholder entry for the closing tag instead of the captured distribution. extract_score finds no scale letter in a placeholder and returns 0.5.

4 · Fix

Two changes, submitted upstream as PR #7 with root-cause writeup in issue #5. (1) The letter falls back to message.reasoning / message.reasoning_content when content is empty. (2) An empty token can no longer re-match the tag in _find_tag_logprobs, so a captured distribution cannot be shadowed by the closing-tag placeholder regardless of which field the letter arrives in. The DeepSeek-API and Gemini code paths are unaffected: content is populated there, and the hardening only skips empty tokens.

5 · Measured Results

All runs on the cluster, model judging its own outputs, temperature 1.0 at the verifier as shipped. After the fix, a pairwise comparison of a correct string-reversal against a broken one scores 0.91 / 0.73. In a best-of-3 over Fibonacci implementations (iterative-correct, exponential-correct, formula-wrong), the incorrect candidate ranks last in both configurations tested; separating the two correct candidates on efficiency requires averaging: at one evaluation pass per criterion the selection is noise, at four passes it resolves correctly. Cost scales linearly: 30 calls / 8.6 min at one pass, 120 calls / 26 min at four. The library's cache-oriented prompt layout (shared prefix, criterion text at the tail) achieved a 53% prefix-cache hit rate against the server's --enable-prefix-caching.

6 · Deployment

Given ~26 minutes per reliable selection, the patched library is deployed on the cluster as an unattended batch utility rather than an interactive component. The tool accepts a task, generates N candidates from the cluster at a spread of temperatures for diversity, then runs verifier selection at four evaluation passes with concurrency capped to the server's scheduling limit. Each run archives all candidates, per-candidate scores, the winning output, and full token accounting. The installation is an editable checkout of the PR branch, so it tracks the upstream fix directly.
